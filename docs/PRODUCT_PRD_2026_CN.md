# AI PC Build Advisor 完整产品需求文档

> 版本：2026-10-25 本地工作版  
> 状态：产品方向与下一阶段实施依据；不代表已上线承诺  
> 本轮边界：仅本地分支，不部署、不 push  
> 标记规则：**[已实现]** 指本仓库已有可运行代码；**[本轮实现]** 指当前本地分支新增；**[规划]** 指尚未实现。

## 1. 一句话定位

AI PC Build Advisor 不是“会聊天的装机清单生成器”，而是一个**有证据、有边界、可回溯的个人计算设备决策工作台**：把模糊需求转成配置，解释预算与性能取舍，用确定性规则验证兼容性，并帮助用户把配置安全地推进到购买、搭建与后续反馈。

长期范围覆盖三条逐级增强的产品线：消费级自组 PC、本地 AI/创作工作站、个人或小团队的桌边 AI 节点。第三类不等同于通用企业服务器配置器。

## 2. 项目最终结果

用户最终得到的不是一段 AI 回答，而是一份持续更新的“决策档案”：

1. 可执行的结构化需求，包括预算、工作负载、偏好、现有部件与风险容忍度。
2. 一套逐项可解释的配置，每个关键数值都有来源、时间与置信度。
3. 通过确定性规则检查的兼容性结果，以及尚不能确定的人工复核项。
4. 可交互的替换和多方案比较，所有替换先预览整机影响，再由用户确认。
5. 按零件拆分的购买计划，保留精确型号、候选商家、价格新鲜度、未知运费与联盟披露。
6. 保存、分享、导出、复盘和实际装机反馈，让后续推荐能够学习真实结果。

成功形态是“从不知道怎么买，到知道为什么这样买，并能放心执行”，而不是最大化聊天轮次或单次点击佣金。

## 3. 当前仓库状态

### 3.1 已实现

- **需求与推荐**：自然语言需求解析、Demo Starter、结构化推荐 API、预算和用途输入。
- **决策工作台**：三栏工作区、零件详情、搜索/替换、2–4 项比较、整机影响预览、显式确认。
- **兼容性与信任**：确定性规则引擎、pass/warning/fail、置信度、来源类型、更新时间、未知值与 disclosure。
- **价格**：精确 canonical part ID 隔离的历史价格契约；开发样本趋势 UI；Best Buy 只读 current-offer provider 边界和显式 SKU 映射，但生产映射为空。
- **购买执行**：购物清单、按商家分组、复制/导出、官方页与搜索参考、联盟披露；未知购买 URL 不伪造成可购买。
- **AI**：mock/OpenAI provider 抽象、结构化建议动作、对话解释、用户确认后才应用修改。
- **持久化**：访客本地会话、Supabase 路径、保存/恢复配置、未保存状态。
- **学习闭环**：post-build feedback 数据模型与表单。
- **商业化基础**：Stripe/Pro feature lock 和用量结构存在，但尚不应视为已验证商业模式。
- **质量保障**：TypeScript、Vitest、构建流程、API 与兼容性测试。

### 3.2 本轮本地实现

- 新增“Build at a glance”三状态卡：预算、兼容性、购买准备度可直接进入下一步。
- 预算分配改为视觉成本条和高支出优先列表；较小类别渐进展开；每个类别仍可进入原比较流程。
- 性能、价值、功耗、PSU 余量与 provenance 保留在默认收起的技术详情中。
- 新增服务端渲染测试，保护状态、来源说明和所有比较入口。

### 3.3 明确尚未实现

- 广覆盖、可承诺 SLA 的实时零售价格和库存。
- 自动抓取第三方商店页面；本产品不应以未获许可的 scraping 作为核心数据来源。
- Amazon Creators API、eBay Partner Network 或多商家生产接入。
- 用户粘贴任意外站配置链接后的稳定解析与精确型号消歧。
- 本地 AI 模型容量/吞吐估算器、双 GPU 拓扑、ECC/IPMI/冗余电源等工作站/节点级规则。
- 价格提醒、库存提醒、自动购买、站内结算。
- 经过留存与付费实验验证的商业模式。

## 4. 用户与核心场景

### Persona A：首次装机用户

- 需要：少做错误决定，知道“为什么”，得到清晰下一步。
- 害怕：型号不兼容、AI 胡说、价格失真、买完才发现缺配件。
- 产品策略：默认低密度、可视化状态、一次只处理一个决策。

### Persona B：有经验的游戏/创作用户

- 需要：快速比较性能、价值、噪音、功耗和升级路径。
- 产品策略：保留完整规格、替换预览、精确来源和高级筛选，不强迫聊天。

### Persona C：本地 AI 开发者/创作者

- 需要：依据模型、量化、上下文、并发和软件栈选择 VRAM、内存、存储与 GPU。
- 产品策略：从“GPU 性能优先”切换为“能否装下、能否稳定跑、每秒成本、数据隐私与扩展性”。

### Persona D：个人实验室/小团队技术负责人

- 需要：常开推理、共享访问、远程管理、备份、网络、噪音与能耗边界。
- 产品策略：先做有边界的“桌边 AI 节点”向导；超出单机/双 GPU 和消费级电气环境时转专家流程。

## 6. 目标与非目标

### 6.1 12 个月目标

- 建立“需求 → 推荐 → 比较 → 验证 → 购买计划 → 反馈”的可测闭环。
- 建立精确型号、规则、报价、证据和用户结果之间的知识图谱。
- 在消费级装机中形成“最可解释、最可信”的差异化。
- 验证本地 AI 工作站场景是否有更高留存和付费意愿。

### 6.2 非目标

- 不承诺覆盖所有国家、零售商、税费、优惠券和组合折扣。
- 不让 LLM 自行决定硬件兼容性或改写用户配置。
- 不在 MVP 做通用机架服务器、SAN、集群调度或企业采购系统。
- 不以“最低价”作为唯一优化目标。
- 不为提高佣金隐藏更便宜方案或来源不确定性。

## 7. 产品原则

1. **规则先于生成**：接口、尺寸、功率等由确定性规则判定；AI 只解释和提出候选动作。
2. **未知就是未知**：缺少运费、库存或型号映射时显示 unresolved，不补零、不猜测。
3. **精确身份优先**：canonical part、MPN、SKU、UPC/GTIN 优先于名称模糊搜索。
4. **先结论后证据**：默认展示三到五个决策状态，技术细节渐进展开。
5. **先预览再修改**：AI、替换、导入都先生成 diff，用户确认后落地。
6. **商业关系可见**：联盟链接在同屏、靠近链接处披露，排序不能被佣金秘密控制。
7. **用户拥有决策档案**：可导出、可分享、可删除，不锁在聊天记录里。

Micro Center 的官方 Builder 已展示兼容过滤、可分享清单、库存和付费装机服务；Puget 将本地 AI 工作站与预验证软件包、专家服务绑定。这说明壁垒不在“能生成一张清单”，而在**可信验证、工作负载知识、执行服务和真实结果数据**。[Micro Center Builder](https://www.microcenter.com/site/content/custom-pc-builder.aspx) · [Puget AI Workstations](https://www.pugetsystems.com/solutions/ai/develop/)

### 8.1 可持续壁垒

- **决策图谱**：需求 → 零件理由 → 规则结果 → 替换 → 最终购买 → 实际反馈。
- **证据层**：每个价格、规格、规则和 AI 结论的来源、新鲜度、置信度。
- **替代品引擎**：不仅找同类零件，而是计算整机预算、兼容性、功耗和风险变化。
- **本地 AI workload 模型**：模型大小、量化、上下文、并发、VRAM/RAM、吞吐和软件栈的结构化映射。
- **结果数据**：真实装机是否成功、噪音/温度/稳定性、模型是否跑通；这是纯内容站难复制的数据。

## 9. MVP 范围

### 9.1 MVP 必须包含

- 需求向导和可编辑需求摘要。
- 三个结果层级：推荐方案、便宜方案、升级方案。
- 可解释预算分配和兼容性状态。
- 关键零件对比与整机影响预览。
- 精确来源、价格时间、非实时提示和未知状态。
- 保存、分享/导出、购物计划。
- 用户粘贴文本/CSV/PCPartPicker 风格清单的导入预览；第一阶段不承诺任意 URL 自动抓取。
- 本地 AI 模式的单 GPU 配置向导。

### 9.2 MVP 后置

- 双 GPU、Threadripper PRO/Xeon、ECC 和远程管理建议。
- 商家 API 广覆盖、价格提醒和区域化税费。
- 桌边 AI 节点的常开运行评估。
- 专家审单市场和企业团队空间。

## 11. 核心交互流程

### 11.1 从零开始

1. 用户选择用途卡或输入一句需求。
2. AI 仅把输入解析为结构化字段；页面展示可编辑摘要。
3. 确定性推荐服务生成三套候选配置。
4. 用户进入工作台，首先看到预算、兼容性、购买准备度。
5. 点击状态卡进入最大支出比较、兼容性 finding 或购物计划。
6. 替换前显示总价、预算余量、兼容性、功耗和性能变化。
7. 用户确认后重新跑规则并记录 decision event。

### 11.2 导入单个用户的配置单

1. 接受文本、Markdown、CSV、JSON；URL 仅在有合法适配器时读取。
2. 解析品牌、型号、MPN、数量和用户声明价格。
3. 以 exact identifier 匹配 canonical part；名称匹配只能产生候选。
4. 歧义项进入“需要确认”队列，绝不静默替换近似型号。
5. 补跑完整性、兼容性和功率规则。
6. 为每个精确零件查找官方页、获许可 API 报价或安全搜索入口。
7. 用户确认后保存为自己的决策档案。

结论：**可以为单个用户把一张配置单落成采购计划**，前提是将“用户提供的零件身份”和“平台实时验证的报价”分开记录。用户给出的商家 URL 可作为该用户的参考证据，但不自动升级为全站可信产品数据。

### 11.3 非聊天 AI 入口

- “解释为什么”：零件卡上的按需解释。
- “如果换成……”：比较面板中的结构化影响总结。
- 需求表单自动补全：从一句话提取预算、应用、显示器和偏好。
- 一键健康检查：发现不平衡支出、风险和信息缺口。
- 导入消歧：把模糊型号转成候选卡，让用户选择。
- 情境建议卡：预算超标、显存不足、库存不可用时出现。
- 装机后诊断：依据温度、崩溃和用户反馈生成排查步骤。
- 专家交接摘要：把完整证据包交给人工顾问。

聊天保留为探索入口，但不应占据默认界面中心。

## 12. AI 架构与工具边界

### 12.1 架构

```text
用户操作 / 表单 / 导入
        ↓
意图与需求结构化（LLM，可失败降级）
        ↓
候选生成与解释（LLM + 检索）
        ↓
确定性领域服务
├─ canonical part identity
├─ compatibility rules
├─ budget / power calculations
├─ offer validation and freshness
└─ policy / provenance validation
        ↓
结构化 proposal / diff
        ↓
用户确认 → 写入 decision ledger
```

OpenAI Responses API 支持状态化交互、内置工具和 function calling；Structured Outputs 可约束为 JSON Schema。这里应把模型输出限制为 `requirements_patch`、`comparison_explanation`、`substitution_proposal`、`evidence_request` 等 schema，而不是让模型直接写入 Build。[Responses API](https://developers.openai.com/api/reference/responses/overview) · [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

### 12.2 AI 可以做

- 解析、总结、解释、提出候选、生成检索查询、标注需要更多信息。
- 调用只读工具查询 canonical catalog、规则结果和报价。
- 返回严格结构化 proposal。

### 12.3 AI 不可以做

- 宣称未经规则验证的兼容性。
- 把相似型号当作同一 SKU。
- 把未知运费当作 0，或把过期报价称为当前最低价。
- 未经用户确认替换部件、保存配置、打开付费结算或发送外部请求。
- 将联盟佣金作为隐藏排序特征。

### 12.4 评估

- 需求字段提取准确率。
- 工具选择与参数准确率。
- 型号消歧正确率和“应当拒答/追问”召回率。
- 引用与来源一致率。
- proposal 经规则引擎拒绝的比例。
- 人工评审的解释清晰度和交易中立性。

生成式系统不能只做普通单元测试；官方 OpenAI 文档建议采用任务特定、持续运行并与人工判断校准的 eval。[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 13. 零部件数据库、来源与刷新

### 13.1 核心实体

- `CanonicalPart`：平台稳定 ID、品牌、型号、MPN、GTIN、类别。
- `PartSpecification`：字段值、单位、来源、抓取/发布/验证时间。
- `CompatibilityAssertion`：规则版本、涉及类别、结果、证据、测试状态。
- `RetailListing`：商家、商家 SKU、精确映射、URL、卖家、condition。
- `OfferObservation`：商品价、运费、税前有效价、库存、时间、来源类型。
- `UserProvidedEvidence`：用户粘贴的价格、URL、截图或清单；默认只对该用户有效。

### 13.2 来源优先级

1. 制造商规格与手册。
2. 获许可的零售商 API/产品 feed。
3. 平台人工核验映射。
4. 用户提供证据。
5. 社区内容，仅作线索，不直接成为兼容性真值。

### 13.3 刷新策略

- 静态规格：发布后抓取，30–90 天复核；重大勘误立即失效。
- 兼容规则：随新平台、BIOS、连接器与测试案例发布版本。
- 当前报价：按 provider 条款、配额和 TTL；页面显示获取时间。
- 历史报价：保留 observation，不把稀疏点画成连续市场事实。
- 用户证据：记录提供时间，不参与全站排序，除非人工升级。

## 14. 外部购物链接策略

### 14.1 门槛判断

- **普通官方产品页/商家搜索页**：可作为非联盟参考，但必须避免“实时库存/最低价”承诺，并在新标签页打开。
- **深链联盟 URL**：需要加入对应计划、使用其授权链接格式并就近披露。
- **目录、价格和库存 API**：通常需要账号、密钥、配额与条款；生产接入不等同于能在网页上手工找到商品。
- **站内结算**：要求更高的商业审批、支付、退货、税务和合规能力；不进入近期路线。

Best Buy Products API 提供价格、可用性、规格和图片；Creator Program 通过 Impact 审核后提供跟踪链接，并要求联盟披露。Amazon Creators API 要求加入 Associates 且近 30 天至少 10 笔合格销售，意味着冷启动阶段不能依赖 Amazon API。Newegg 联盟计划支持 deep link，但需申请审核；eBay Browse API 的生产和联盟 URL 也有 Partner Network 要求。[Best Buy APIs](https://developer.bestbuy.com/apis) · [Best Buy Creator FAQ](https://www.bestbuy.com/site/best-buy-affiliate-program/creator-program-faqs/pcmcat1741639882344.c?id=pcmcat1741639882344) · [Amazon Creators API](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/introduction) · [Newegg Affiliate](https://www.newegg.com/promotions/affiliate_program/affiliate.html) · [eBay Buy API Requirements](https://developer.ebay.com/api-docs/buy/buy-requirements.html)

### 14.2 推荐落地顺序

1. 继续支持官方页和编码后的商家搜索 URL；明确“参考入口，不是实时报价”。
2. 人工核验少量高频 exact SKU，接 Best Buy 只读 API pilot。
3. 申请 Best Buy/Newegg 联盟，验证披露、点击和转化链路。
4. 有稳定流量与销售后申请 Amazon Creators API。
5. eBay 仅用于可控品类和卖家/condition 风险可清晰呈现的场景。
6. 每个报价都做 click-time refresh；失败时回退到搜索，而不是保留虚假“购买”按钮。

## 15. 兼容性规则与验证

### 15.1 消费级基础规则

- CPU socket ↔ motherboard socket/chipset/BIOS。
- RAM generation、DIMM 类型、容量与主板支持。
- GPU/散热器/主板 ↔ 机箱尺寸和插槽。
- PSU wattage、瞬时余量、连接器和 ATX 版本。
- 存储接口、lane sharing、可用 M.2/SATA 插槽。
- 散热器 TDP、安装扣具、冷排位置、RAM clearance。
- 前面板、USB header、风扇/RGB controller 等完整性规则。

### 15.2 验证方法

- 规则必须版本化并附正/反/边界测试。
- `fail` 只用于确定性阻断；`warning` 用于 BIOS、尺寸容差、未知 connector 等需复核项。
- 推荐结果和每次替换后都重跑整机规则。
- 高风险/新平台使用 golden builds 做回归。
- UI 同时显示结论、受影响部件、规则来源与建议动作。

## 16. 本地 AI、工作站与桌边节点路线

### 16.1 产品分层

| 层级                   | 典型用户                       | 近期支持            | 关键约束                                            |
| ---------------------- | ------------------------------ | ------------------- | --------------------------------------------------- |
| AI-capable consumer PC | 轻量本地推理、创作、游戏       | **MVP**             | 单 GPU、VRAM、驱动/OS、噪音、预算                   |
| AI workstation         | 开发、RAG、生成媒体、训练/微调 | **下一阶段**        | 1–2 GPU、PCIe lanes、VRAM/RAM、供电、散热、容器栈   |
| Desktop AI node        | 小团队常开推理/agent           | **探索**            | 远程管理、10GbE、访问控制、备份、UPS、TCO、持续负载 |
| 通用服务器/集群        | 企业生产与大规模训练           | **非目标/专家转介** | 机架、电力、冗余、网络架构、SLA、合规               |

### 16.2 不把 NPU、GPU 和服务器混为一谈

Copilot+ PC 的 NPU 门槛是 40+ TOPS，适合经 Windows ML 优化的端侧功能；它不能替代大模型所需的 GPU/统一内存判断。[Microsoft Copilot+ developer guide](https://learn.microsoft.com/en-us/windows/ai/npu-devices)

本地生成式 AI 的首要筛选应是模型容量和 GPU/统一内存。NVIDIA 当前官方对比把 GeForce RTX 定位到最高 32GB VRAM、约 50B 模型容量；DGX Spark 使用 128GB 统一内存并面向更大模型与常开 agent。产品应将这些作为硬件类别示例，而不是保证任意模型都能达到特定速度。[NVIDIA Local AI](https://developer.nvidia.com/topics/ai/local-ai) · [DGX Spark Hardware](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)

### 16.3 新增需求字段

- model family、参数规模、量化格式。
- context length、并发用户、tokens/s 或完成时间目标。
- 推理 / LoRA / 全量训练 / 图像 / 视频 / RAG。
- 数据集大小、热数据与归档策略。
- Windows/Linux、CUDA/ROCm/DirectML/Windows ML 偏好。
- 单机交互或 24×7 服务；本地网络和远程访问。
- 噪音、电力回路、UPS、空间和散热环境。
- 数据隐私、加密、备份和访问控制。

### 16.4 专项规则

- 模型权重 + KV cache + runtime overhead 的内存预算必须拆分展示。
- 多 GPU 不能简单相加性能：检查框架支持、互联、lane、电源和并行策略。
- 2 张高功耗 GPU 自动要求电气、机箱、散热和噪音复核。
- 常开节点要求 UPS、网络、远程恢复、备份与最小权限清单。
- 需要 ECC、BMC/IPMI、冗余电源或 3 张以上 GPU 时进入专家模式。

## 17. 技术架构

### 前端

- TanStack Start + React + TypeScript + Tailwind/CSS。
- 工作台状态使用 typed domain model；UI 只消费归一化实体。
- 渐进披露、键盘可达、窄屏单面板导航。

### 服务端

- API Router → domain services → providers/repositories。
- Provider adapter 隔离 Best Buy、未来 retailer、OpenAI 与 persistence。
- 所有第三方 secret 仅在 server 环境；禁止 `VITE_` 暴露。

### 数据层

- Postgres/Supabase：用户、需求、build、decision event、feedback。
- 产品目录和规则需要独立版本表；offer observation 采用 append-only。
- 缓存键包含 canonical part、provider、market、condition 和 location scope。

### 可观测性

- 记录 provider latency、cache hit、mapping miss、stale offer、规则版本。
- AI 记录 schema、模型、工具调用、拒绝/降级和 token/cost，但不记录不必要的敏感文本。
- 业务事件围绕“完成一个决策”而非点击量。

## 18. Metrics

### North Star

**Verified Decision Completion Rate**：开始配置的用户中，完成“需求确认 + 兼容性查看 + 至少一次保存/导出/购物计划”的比例。

### 激活

- 首次生成成功率、首次有意义交互时间。
- 需求摘要确认率。
- 至少一次比较/替换预览率。

### 信任与质量

- exact identity 覆盖率、source coverage、报价新鲜度。
- 规则引擎 false positive/negative 报告率。
- AI proposal 被规则拒绝率。
- unresolved 状态被正确呈现率；错误 live-price claim 必须为 0。

### 留存与结果

- 7/30 天回访率、保存配置恢复率。
- 装机后反馈提交率、成功点亮率、首次运行目标 workload 成功率。
- 被替换部件的主要原因分布。

### 商业

- 购物计划打开率、出站点击率、每完成决策收入。
- 付费咨询转化、Pro 留存、退款率。
- 必须同时监控“高佣金链接是否获得异常排序曝光”。

## 19. 变现路径

近期应优先验证信任和留存，不把联盟佣金设为唯一目标。

1. **联盟佣金**：低摩擦，但易受计划审批、cookie、品类费率和退货影响。
2. **Pro 订阅**：多配置、价格/库存提醒、高级工作站评估、团队分享、长期变更追踪。
3. **一次性专家复核**：复杂工作站、双 GPU、静音/小机箱、桌边节点；平台生成证据包，专家签审。
4. **装机/迁移 lead fee**：转介本地装机、数据迁移、家庭网络、远程部署。
5. **B2B workspace**：审批模板、标准镜像、共享零件白名单、TCO、审计记录。
6. **数据/API**：向集成商提供结构化需求、兼容性和 substitution 服务；必须避免出售个人行为数据。
7. **厂商赞助**：只允许明确标注的 sponsored slot，不混入自然推荐排序。

建议顺序：免费闭环 → 专家复核试点 → Pro 工具 → 联盟规模化 → B2B。先证明用户会保存、回来并执行，再优化 monetization。

## 20. Roadmap

### Phase 0：可信 MVP 收口（0–6 周）

- 完成当前低密度 UI，补浏览器级交互测试和窄屏视觉验收。
- 将“开发样本价格”与 current offer 状态统一成来源组件。
- 配置导入支持文本/CSV/JSON，完成 exact identity 消歧队列。
- 建立 North Star 与 trust metrics。

### Phase 1：采购可执行（6–12 周）

- Best Buy 少量 verified SKU pilot。
- 申请 Best Buy/Newegg 联盟；实现 click-time refresh 和同屏 disclosure。
- 分享码、只读公开配置、购物计划 diff。
- 价格提醒仅在 provider SLA、用户同意和取消机制完成后上线。

### Phase 2：本地 AI 工作站（3–6 个月）

- workload schema、VRAM/RAM 可行性、单 GPU 推荐。
- 模型/量化容量解释器和软件栈兼容矩阵。
- 真实任务 benchmark 与用户反馈闭环。
- 专家复核试点。

### Phase 3：桌边 AI 节点与 B2B（6–12 个月）

- 双 GPU、lane/NUMA/供电/热规则。
- 常开服务 TCO、10GbE、UPS、备份和访问控制清单。
- 团队空间、审批、标准配置和生命周期管理。
- 超出边界时转集成商，而不是自动生成高风险服务器方案。

## 21. 风险与缓解

| 风险               | 影响               | 缓解                                               |
| ------------------ | ------------------ | -------------------------------------------------- |
| 价格/库存过期      | 误购、信任损失     | TTL、时间戳、click-time refresh、未知回退          |
| 型号误匹配         | 买错零件           | exact identifier、显式映射、消歧确认               |
| AI 幻觉            | 错误兼容或性能承诺 | schema、只读工具、规则引擎、用户确认、eval         |
| 联盟计划拒绝/变更  | 商业模型不稳定     | 多来源、非联盟搜索回退、收入多元化                 |
| 界面再次变密       | 初学者流失         | 默认三状态卡、渐进披露、任务完成测试               |
| 工作站建议超出能力 | 高价值事故         | 产品边界、专家模式、验证矩阵、免责声明不能替代规则 |
| 社区/用户数据污染  | 错误全站知识       | 用户证据隔离、人工升级、来源权重                   |
| 商业偏见           | 推荐可信度下降     | 排序特征透明、佣金与推荐分离、审计指标             |

## 22. Open Questions

1. 首发市场是否只做美国 USD？这决定零售商、税费、运输和联盟策略。
2. 用户更愿意为“持续提醒”还是“一次专家复核”付费？
3. 分享配置是否公开索引，还是默认私密链接？
4. 导入外站 URL 的允许列表从哪些站开始，如何处理其条款变化？
5. 本地 AI 推荐首先支持哪些 runtime：Ollama、vLLM、llama.cpp、ComfyUI？
6. benchmark 以公开数据、平台实测还是用户遥测为主？
7. 双 GPU 进入自助产品的安全门槛是什么？
8. 是否与本地装机店合作承担最终物理 fit 检查和售后？
9. 用户能否选择“不出现任何联盟链接”的中立模式？
10. 哪些 post-build 数据足以提升推荐，又不会造成过度收集？

## 23. 下一轮推荐决策

下一轮不要继续扩页面数量。优先完成两件事：

1. **导入并核验一张真实用户配置单**：证明单用户采购链路可行，同时暴露 identity 和来源缺口。
2. **定义 Local AI Workload Schema + 容量计算原型**：验证“本地 AI 工作站”是否能形成比通用装机网站更强的产品价值。

这两项分别验证采购闭环和差异化壁垒；在完成前，不建议把主要资源投入更复杂的聊天机器人或大规模服务器目录。
